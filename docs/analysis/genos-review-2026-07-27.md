# Инженерное ревью GenOS

Дата: 2026-07-27

Область ревью: планировщик, таймеры, ожидания и сигналы, VFS/resources,
POSIX-слой, TTY, host-тесты и STM32 test applications.

Это статическое ревью. Изменения в исходный код ядра не вносились. Штатный
запуск host-тестов:

```sh
python3 make.py runtests -j4
```

завершается ошибкой:

```text
ModuleNotFoundError: No module named 'licant'
```

## Резюме

GenOS представляет собой компактный cooperative runtime с
процессоподобной моделью, VFS/POSIX-фасадом, таймерами и TTY. Основа хорошо
соответствует MCU:

- intrusive lists не требуют аллокаций внутри планировщика;
- автоматные и стековые задачи разделены;
- аппаратно-зависимый context switch вынесен за границу ядра;
- timer manager, namespace и line discipline имеют небольшие интерфейсы;
- присутствуют host stub и реальные STM32F4/STM32H7 приложения;
- execution monitor даёт полезную телеметрию исполнения задач.

Главный технический долг сосредоточен в управлении временем жизни объектов и
атомарности переходов между состояниями `run`, `wait` и `final`.

## Найденные дефекты

### 1. Namespace принимает частичное совпадение пути

Приоритет: критический  
Kanboard: #931 `[vfs] Исправить частичное совпадение namespace`

В `genos/resource/lookup.cpp` namespace считается подходящим при любом общем
префиксе. Например, зарегистрированный `/dev` может получить запрос `/data`,
поскольку совпал символ `/`.

Namespace должен приниматься только при полном совпадении зарегистрированного
префикса. После префикса допустим только конец строки или `/`; среди корректных
кандидатов должен выбираться самый длинный.

### 2. Жизненный цикл файловых дескрипторов не замкнут

Приоритет: критический  
Kanboard: #932 `[vfs] Восстановить lifecycle файловых дескрипторов`

Текущая реализация имеет несколько связанных нарушений:

- `openres::open()` не вызывает `file->on_open()`;
- неудачный `open()` оставляет занятый элемент `resource_table`;
- `close()` объявлен, но не реализован;
- `release()` не обнуляет `file`;
- очистка таблицы не вызывает `on_release()` для открытых ресурсов;
- `copy_open_resources_from()` может разыменовать `nullptr` после неудачного
  `open()`;
- переполнение `static_vector<openres, 5>` молча возвращает существующий
  последний слот вместо ошибки.

Для TTY отсутствие `on_open()` означает, что PID, GID и reference counter не
устанавливаются.

### 3. Приоритет позволяет выйти за границы runlist

Приоритет: критический  
Kanboard: #933 `[sched] Ограничить диапазон приоритетов`

`schedee::set_priority()` принимает произвольный `uint8_t`, после чего значение
напрямую используется как индекс массива `runlist` размером
`SCHEDEE_PRIORITY_TOTAL`. Приоритет `>= 3` приводит к повреждению памяти.

API должен исключать или явно отклонять значения вне диапазона, а инвариант
следует защищать непосредственно перед индексированием.

### 4. Возможна потеря пробуждения при чтении TTY

Приоритет: высокий  
Kanboard: #934 `[tty] Устранить потерю пробуждения при read`

`tty::read()` и `zillot_chardev::read()` сначала проверяют `avail()`, а затем
отдельно ставят текущую задачу в wait queue. UART IRQ между этими операциями
может добавить данные, не найти ожидающего и оставить задачу спящей навсегда.

Проверка условия и постановка в очередь ожидания должны быть атомарны
относительно RX IRQ.

### 5. kill не завершает ожидающие задачи

Приоритет: высокий  
Kanboard: #935 `[sched] Завершать убитые ожидающие задачи`

`schedee::kill()` только устанавливает флаг `killed`, а scheduler проверяет его
только для задач из `runlist`. Задача в timer wait, wait queue, `waitpid()` или
TTY wait не завершится до внешнего пробуждения; если событие не произойдёт, она
останется навсегда.

Завершение должно атомарно удалить задачу из прежней управляющей очереди и
исключить поздние timer/waiter callbacks к уничтоженному объекту.

### 6. Finalization может вызвать нулевой destructor callback

Приоритет: высокий  
Kanboard: #936 `[sched] Сделать finalization безопасной без callback`

`remove_without_zombie_state` включён по умолчанию, но destructor callback у
`autom_schedee` и `coop_schedee` может быть `nullptr`.
`schedee_manager_step()` вызывает callback без проверки. Напрямую созданная
stack/static `coop_schedee` поэтому может упасть после возврата из задачи.

Политику владения динамическими и статическими schedee следует выразить явно;
finalization не должна зависеть от неявного соглашения фабрик.

### 7. Timer manager имеет гонку с IRQ

Приоритет: высокий  
Kanboard: #937 `[timer] Закрыть гонку manager с IRQ`

`ktimer_manager_step()` получает указатель на первый таймер под `system_lock`,
снимает lock и только затем проверяет и удаляет таймер. IRQ в этом окне может
перепланировать или изменить объект, нарушив порядок списка и время жизни
указателя.

Проверка дедлайна и извлечение истёкшего таймера должны быть атомарными, а
callback следует вызывать уже без глобального lock.

### 8. waitpid может потерять уже завершённого ребёнка

Приоритет: высокий  
Kanboard: #939 `[proc] Не терять уже завершённых детей в waitpid`

`waitpid()` безусловно переводит родителя в `wait_schedee` и не хранит состояние
ранее завершённых детей. Если ребёнок завершился до вызова `waitpid()`,
`SIGCHLD` уже потерян и родитель засыпает навсегда.

Кроме того, код завершения ребёнка не сохраняется и не возвращается. Нужна
явная zombie/reap policy с определённым поведением для неизвестного PID,
повторного ожидания и нескольких детей.

## Сборка, тесты и незавершённые API

Kanboard: #938 `[build] Восстановить воспроизводимые host-тесты`

README пуст, внешние зависимости и их совместимые ревизии не зафиксированы.
В CI зависимости извлекаются из текущих головных веток. Из host-тестов активны
только пять сценариев; namespace/VFS-тесты закомментированы. Старый тест
`/pr -> nullptr` как раз обнаружил бы ошибку частичного совпадения namespace.

Публичный слой также содержит явные заглушки:

- `send_signal_to_group()` ничего не делает;
- `select()` вызывает `BUG()`;
- `system_v()` вызывает `abort()`;
- `access()` всегда сообщает успех;
- shell сразу завершается.

Эти функции следует либо реализовать, либо явно пометить как неподдерживаемые,
чтобы внешнее API не обещало отсутствующую семантику.

## Рекомендуемый порядок работ

1. Восстановить воспроизводимый host build и базовый test loop.
2. Исправить namespace и lifecycle файловых дескрипторов.
3. Закрыть потерю пробуждения TTY.
4. Укрепить инварианты scheduler: диапазон приоритетов, kill и finalization.
5. Сделать timer manager безопасным относительно IRQ.
6. Определить zombie/reap policy и исправить `waitpid()`.
7. После стабилизации ядра разобрать неподдерживаемые POSIX/system API.

Для конкурентных дефектов host-тестов недостаточно: TTY wakeup и timer manager
нуждаются также в целевых stress/smoke проверках на STM32.
